publish-bounded-regex

OpenSpec design | 2026-10-31 | Implemented and verified | Owning epic smithy-2qe.60

Create moonrockz/regex as a core-only library for bounded Boolean search. Compile the program once and create fresh, metered execution state per call. Smithy keeps its dialect translation and maps exhaustion into its shared validation budget.

Context

See the proposal for motivation and the capability spec for observable behavior. The investigation is recorded on smithy-2qe.60. The existing engine in pkgs/smithy-validation/internal/regex comes from core d3c49d1; seven modified files and added meter/front files provide interruption, charge replay and cache limits.

Core 0.10.18, commit 417988f6e19738a7f683ce19a6cf5aaf52c96965, represents the program as a tagged NFA and builds DFA transitions lazily. Its internal cache allowance does not limit match work. Public @string.Regex exposes no budget. Compiler-known lexmatch cases cannot accept runtime model patterns.

The current validation adapter passes remaining work into the matcher in validate.mbt, lines 206 through 217. The Morphir acceptance cases and exact-boundary laws prevent replacing actual work with an overly pessimistic length multiplier. The isolated consumer script explicitly maps local modules, so adding a sibling import also requires updating that dependency closure.

Goals and non-goals

The reusable boundary contains no shape IDs, findings, Smithy model loader, async runtime or generated application code. Private upstream packages remain private. Initial support is runtime Boolean search with the core dialect; consumers that require another dialect translate or reject it at their own boundary.

Capturing-group syntax can serve as grouping because the API returns no captures and the dialect has no backreferences. Extraction, token scanning, replacement, splitting, full ECMA conformance and generated lexmatch are separate extensions. The release tooling will know the module; this work does not publish it.

Decisions

PKG-1. A public module with private vendored packages

Use pkgs/regex and module name moonrockz/regex, selected by the user. Put the public API and checked examples at the module root and source copies under internal/. Keep upstream package layout recognizable. Bring over only the parser, engine, AST, symbol mapping, shared types, character-set support, UTF-16/profile code and tests required by this Boolean implementation. Do not copy the old automata package into the final module.

Keeping this inside smithy-validation would retain the unwanted dependency. Publishing a separate repository would add release and source-management work without improving the API boundary. This monorepo already publishes independent modules such as jmespath.

API-1. Validated inputs and explicit exhaustion

The public vocabulary is Regex, CompileLimits, WorkLimit, MatchOutcome and structured compilation/configuration errors. Proposed operations are Regex::compile(pattern, limits~) and Regex::matches(input, work~). A completed outcome carries matched and used; an exhausted outcome carries used. Hide counters and engine objects behind those types.

Validate work limits in the range 0 through 10,000,000; zero represents an already-spent caller allowance. Default compilation caps are 4,096 source UTF-16 units, 32 nested groups and 1,024 expanded expression units. Support finite configurable maxima of 1,048,576 source units, 64 group levels and 65,536 expanded units. Higher caps let adapters compile expanded translations without changing their source-language limits. Name errors separately for malformed syntax, unsupported constructs and exceeded compilation limits. Do not use None or a Boolean to conflate exhaustion with a completed non-match.

The existing internal (Bool, Int)? API is sufficient for its single adapter but is ambiguous for new consumers. A shared mutable public meter would couple the library to request ownership. Returning used units lets callers compose their own budgets and treat exhaustion as terminal for the current operation.

CMP-1. Bound compilation before expansion

Check source length first. Pass the configured nesting limit into the parser and check it before descending into a group. After parsing, count the expression's expansion with checked arithmetic before emitting NFA copies or constructing symbol tables. Count class intervals and UTF-16 lowering contributions as part of the documented structural bound. Reject over-limit multiplication before allocating the expanded structure.

Use the existing Smithy pattern_size accounting as a compatibility reference, not as a second regex parser in the generic API. The generic bounds operate on the supported core syntax and normalized AST. Erase capture annotations before NFA construction so execution retains only the whole-match tags. Compare Boolean behavior with core using the original pattern, including ordinary and named grouping syntax where supported by the parser.

Core's per-quantifier and group-depth limits alone permit huge nested expansion. Waiting until the first search to build the NFA would place that unmetered expansion inside a supposedly bounded call. Compilation must finish the immutable program under its own finite structural limits.

RUN-1. Share the program, isolate each execution

Split upstream's private compiled-regex state into an immutable program and a per-call runner. The program owns the NFA nodes, symbol map, category data and entry point. The Boolean runner owns visited/targeted stamps, state keys and transition tables. It treats capture tags as epsilon moves, so capture registers and renaming are unnecessary. Every search starts with an empty runner, charges its initialization and discards it on completion or exhaustion. The upstream tagged DFA executor stays unchanged as a private test reference; added bounded.mbt implements the smaller Boolean specialization over the same compiled NFA.

This removes cross-call cache history from both costs and outcomes without transition-cost replay tables. Cache hits within one call still accelerate repeated transitions. Cross-call caching was considered, but register renaming, cache flushes and state reuse make faithful cold-work replay substantially harder in the new engine. Retaining the old engine would postpone the new-engine maintenance while leaving the original migration unresolved.

Fresh execution allocates more often on short repeated inputs. Compile once, retain the immutable program, and measure this cost against realistic Morphir patterns. Do not cache mutable runners as an optimization within this change.

MET-1. Charge every variable-cost execution operation

Precharge input UTF-16 length plus the end marker, preserving the current input-size protection. Charge initialization before allocating scratch storage. During transition construction, charge node and alternative visits, tag/key words examined or copied, symbol-set lookup work and register scans. Charge logical array cells allocated or copied before growth and clearing. Charge state reuse, candidate comparisons and flush work if those paths remain reachable.

Core's general hash maps hide probing, comparisons and resizing from the meter. Use a private meter-aware state index with a specified deterministic integer hash and traversal order, checked growth and charged probes/key comparisons. Apply the same rule to any execution-time shape index, or remove that optimization if its measured value does not justify retaining it. A fixed hash is safe here only because collision work is metered. Do not claim constant-time lookups or rely on process-randomized hash seeds for deterministic units.

Use checked/subtractive allowance comparisons before counter and capacity arithmetic. A refused charge performs no subsequent work for that operation and unwinds to the public exhausted outcome. Compiled programs survive interruption; partial runners never escape. Internal tests can use a very large finite allowance, but the public path has no unbounded execution bypass.

Before the engine group is closed, publish a cost table linking charges to loops and allocation sites, the constant converting charged storage into a bound on reachable matcher storage, and measurements on native plus JS or wasm-gc. Units describe logical work in this implementation, not CPU instructions, allocator overhead, process RSS or an exact deadline. Their numeric values are not preserved across engine versions. Same-version outcomes and units must agree on all four targets.

SMY-1. Preserve the Smithy adapter contract

Keep ECMA escape/class/anchor translation, existing source/nesting/expansion guards and UnsupportedConstraint diagnostics in pkgs/smithy-validation/pattern.mbt. The library is not named or advertised as an ECMA engine. BoundedPattern holds the new public Regex; translate completed outcomes into its current match/count result and exhausted outcomes into the existing stop path. The validation budget still receives only remaining call work and returns incomplete LimitExceeded.

Do not apply the generic default source-length cap to already-translated Smithy text. For example, repeated whitespace escapes expand into long explicit classes. After Smithy's existing guards pass, use the library's larger finite caps as secondary safeguards, and prove that the translator and lowering of every accepted profile pattern fit them. Add a regression with translated text longer than 4,096 units. This keeps the source-language profile stable while leaving generic defaults useful for direct consumers.

The 97-unit FQName, 16 references and deal record remain acceptance gates at 100,000 default units. The old optional-chain regression might legitimately become cheap under the new engine. Preserve it as a differential correctness case; if it no longer exhausts, replace its exhaustion expectation with a measured expensive case in the same supported profile. Keep an explicit inner-transition exhaustion regression. Do not force the old engine's numeric costs onto the new algorithm.

REL-1. Publish through the existing release process

Use the root module's shared version, add the module to moon.work, add the versioned sibling dependency to validation and update both publication lists before smithy-validation. Check version discovery and package inventory mechanically. Extend isolated consumer packaging to stage the new module; add a core-only public consumer alongside the existing validation consumer checks. Prefer the existing script/task over another CI workflow.

Retarget regex:vendor:check to the new module and pinned commit. Preserve the git-environment isolation regression. List every normalization, hook, new private helper and modified upstream test explicitly, with required upstream license/NOTICE text. Tests upstream of the Boolean wrapper may still require internal capture behavior; retain their unchanged paths where possible and explain any necessary adaptation in the hook inventory. Keep runtime dependencies small without removing licensing or useful source tests.

Update README layout, public package docs, AGENTS.md and release documentation. Existing tags continue using their original publication inventory. Publication and version bumps remain normal release actions after the change lands.

Risks and trade-offs

A new cost model rejects useful inputs.Require Morphir acceptance at unchanged limits. Fix the charge model or implementation; do not raise defaults to satisfy the gate.

Migration plan

  1. Establish the independent module, public types and bounded compiler. Keep validation on its existing engine while the replacement is incomplete.
  2. Implement fresh-run metering and prove the public matcher laws and bounds before switching validation.
  3. Switch the private adapter, update consumer dependency closure, verify integration and remove the redundant old engine. Update obsolete algorithm-specific exhaustion fixtures explicitly.
  4. Wire provenance and publication checks and documentation; run the gates in tasks.md. Release through the normal process later.

Before integration, rollback means leaving the existing matcher in use. After integration, revert the adapter/dependency/removal change together; do not leave two active engines or silently fall back after exhaustion. No migration writes external data.

Verification

Use compiler checks for API/type correctness and focused tests for semantics and budget boundaries. Differential tests cover supported patterns, Unicode, anchors, nullable repetitions and capture erasure. Budget laws cover exact limits, zero, overflow rejection, collisions, table growth and recovery. Cross-target fixtures compare both outcomes and counts. Benchmarks include the investigation's backtracking, state-explosion and long-input families, plus useful Morphir models.

Repository gates include the vendor check, isolated consumers, validation/RPC/codec regressions, script publication-inventory checks, strict OpenSpec validation and mise run check. Format changed MoonBit sources before any eventual commit. No commit, push, merge or publication is part of this proposal turn.

Fresh delivery measurements are available as native and JS benchmark evidence, including the source and measurement scope. Publication remains part of the normal release process.
